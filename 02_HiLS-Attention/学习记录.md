## 我们为什么研究 HiLS？

长上下文模型需要利用很远以前的信息。标准全量 Attention 对长度为 (L) 的序列计算 Query 与所有 Key 的相关性，注意力分数规模随 (L^2) 增长。

FlashAttention 通过分块和在线 Softmax 优化 IO，减少注意力矩阵在 HBM 中的读写，但它仍然执行精确稠密 Attention 的主要二次计算。

稀疏 Attention 则尝试减少真正参与计算的连接。一个自然思路是把历史 Token 分成 Chunk，只挑选少量重要 Chunk 做细粒度 Attention。

困难在于：如果为了知道哪个 Chunk 重要，仍然先计算 Query 与 Chunk 内全部 Token 的相关性，那么检索本身就可能很昂贵。HiLS 的核心思路，是先为 Chunk 构造压缩表示，用较低成本估计 Chunk 的注意力质量，再对选中的 Chunk 使用原始 K/V 做细粒度计算。

## Landmark Query：压缩表示从哪里来？

给定一个代表 Chunk 的先验/地标 Query (mu_c)，先计算它对 Chunk 内 Key 的注意力分布：

[
p_j=
operatorname{Softmax}_{j}
left(rac{mu_c^Tk_j}{sqrt d}ight)
]

然后得到加权压缩 Key：

[
k'_c=sum_{j=1}^{S}p_jk_j
]

以及熵偏置：

[
b'_c=-sum_{j=1}^{S}p_jlog p_j
]

直观上：
- (k'_c)：用一个向量概括 Chunk 内部在先验 Query 下的 Key 信息；
- (b'_c)：补充注意力分布的熵信息，描述权重分布是集中还是分散。

这不是普通均值池化。源码还保留了均值池化作为可选替代路径，便于做对照或消融。

因此，Chunk 的近似 log-mass 可以用 Query 与压缩 Key 的内积，再加上熵偏置来估计。

这给出了数学动机：把原来需要访问 Chunk 内多个 Key 的计算，转化为对压缩表示的一次内积。

需要保留的边界：这是在 Landmark Query 附近的一阶近似。Query 偏离展开点时误差可能增大，不能认为对所有 Query 都精确。检索质量和最终模型质量仍需实验验证。

## HiLS 的分层计算：检索与内容读取不是一回事

当前理解可以分成两件事：

1. **检索阶段：** 使用 Chunk 压缩表示 (k'_c) 和偏置 (b'_c) 估计 Chunk 重要性，选择 Top-K。
2. **细粒度计算阶段：** 对选中的 Chunk，仍使用原始 Key/Value 做 Attention，得到真正的内容聚合。

此外，模型保留 Sliding Window Attention（SWA）局部通路。局部窗口负责近邻上下文，检索到的 Chunk 提供远距离信息。两条分支的结果通过权重归一化后合并。

所以不能把 HiLS 简化成“把 K 压缩后直接算输出”。压缩表示主要用于检索；被选中 Chunk 的原始 K/V 仍参与细粒度 Attention。

### 初始化阶段

`__init__` 定义：
- Q/K/V/O 线性投影；
- Query Head 与 KV Head 数量；
- 可选 Landmark Query 投影及归一化；
- Chunk Size、Top-K、Sliding Window；
- RoPE、GQA、KV Cache 等配置；
- 底层 Chunk Pooling、Top-K、SWA 和稀疏 Attention 函数。

GQA 的分组关系：

[
G=H_q/H_{kv}
]

Query Head 数通常是 KV Head 数的整数倍。

### `_project_qkv`

输入：

[
X:[B,L,D]
]

普通投影：

[
Q=XW_Q,quad K=XW_K,quad V=XW_V
]

重排后：

[
Q:[B,L,H_q,d]
]

[
K,V:[B,L,H_{kv},d]
]

若启用独立 Landmark Query 投影，还会产生 (Q_{mathrm{lmk}})。普通 Query 用于当前 Token 的 Attention；Landmark Query 用于构造 Chunk 的压缩表示。二者任务不同，不应混淆。

### `_apply_hils_rope`

根据配置对普通 Q/K 应用 RoPE；独立 Landmark Query 也可以通过对应路径旋转。RoPE 是位置编码处理，不是 Chunk 检索算法本身。

### `_compute_landmark_keys`

将 Key 从：

[
[B,L,H_{kv},d]
]

重排为：

[
[B,N_c,S,H_{kv},d]
]

其中 (N_c=lfloor L/Sfloor)。

源码通常从每个 Chunk 最后一个 Token 位置取 Landmark Query，再调用 `chunk_attn_pool` 生成压缩 Key 和 prior bias。

该函数还处理：
- GQA Head 扩展；
- Prefill/训练时完整 Chunk 的构造；
- Decode 时只对新增完整 Chunk 进行池化；
- 将压缩表示放入 `past_key_values._hils_prior_cache`；
- 均值池化替代路径；
- 不完整尾部 Chunk 的边界情况。

### `forward` 的当前调用链

根据源码阅读，概念流程为：

`hidden_states → Q/K/V 与 Landmark Query → RoPE/Cache → SWA → Chunk Pooling → Top-K → 稀疏 HiLS Attention → 分支融合 → o_proj`

关键调用：
- `flex_attn_tl(...)`：计算 Sliding Window Attention 输出及归一化相关量；
- `_compute_landmark_keys(...)`：生成 Chunk 压缩表示；
- `topk_func(...)`：产生选中 Chunk 的 indices 和 scores；
- 根据 indices gather 对应 prior bias，并加入分数；
- 将 Chunk 分数与局部窗口的归一化信息组合；
- `hils_func(...)`：使用选中 Chunk 的原始 Q/K/V 计算稀疏 Attention；
- 合并局部窗口分支与 HiLS 分支，再执行输出投影。

这是一条概念调用链。实际执行会受到训练/推理模式、Cache、序列长度和配置开关影响。

## 源码中已经遇到的几个重要实现细节

### 1. Chunk Pooling 的 PyTorch 参考实现

在文件顶部的 `_chunk_attn_pool_impl` 中可以看到：
- Landmark Query 与 Chunk Key 转为 FP32；
- 根据 GQA 分组扩展 KV Head；
- 计算 Chunk 内 logits；
- 将 Chunk 内最后一个 Token 对应的 logits mask 为 (-\infty)；
- 沿 Chunk 内 Token 维做 Softmax；
- 计算加权 Key；
- 计算熵偏置；
- 压缩 Key 转回 K 的 dtype，bias 保留 FP32。

这里值得专门研究：调用方从 Chunk 最后一个位置取 Landmark Query，而池化实现又屏蔽 Chunk 内最后一个 Key 位置。需要结合论文和完整配置继续核对其设计动机及边界语义。

### 2. 模型层与算子层的分工

模型层负责组织数据流、检查形状、管理配置和 Cache；底层 Kernel 负责具体张量计算及硬件调度。
